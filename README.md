# 高校实验室设备预约管理系统 V2

> 一个基于 **FastAPI + Vue3** 的前后端分离系统，覆盖设备浏览、在线预约、
> 审核流转、邮件通知、数据统计的完整业务闭环。
>
> 这个版本是对初版的重写

## 一、快速开始

### 前置要求

| 软件 | 版本 | 说明 |
|------|------|------|
| Python | 3.12+ | 后端运行环境 |
| MySQL | 8.0+ | 数据库（需要支持 `caching_sha2_password`） |
| Redis | 任意 | 缓存（可选，不装会降级但功能正常） |
| Node.js | 18+ | 前端构建 |

### 一键搭建

```powershell
cd C:\code\LabBookingSystemV2
.\scripts\setup.ps1
```

脚本会自动：检查软件 → 生成 `.env` → 建虚拟环境 → 装依赖 → 初始化数据库 → 装前端依赖。

**注意**：首次运行会提示你编辑 `backend\.env` 填写数据库密码和 `SECRET_KEY`。

### 启动（三个窗口）

双击 `启动脚本\` 目录下的文件，按编号顺序：

| 文件 | 作用 | 端口 |
|------|------|------|
| `1-启动Redis.bat` | 启动缓存服务 | 6379 |
| `2-启动后端.bat` | 启动 API 服务 | 8001 |
| `3-启动前端.bat` | 启动网页界面 | 5173 |

然后浏览器打开 **<http://127.0.0.1:5173>**

## 二、技术栈

### 后端

| 技术 | 用途 | 为什么选它 |
|------|------|-----------|
| FastAPI 0.115 | Web 框架 | 原生异步、自动生成 OpenAPI 文档、Pydantic 校验集成 |
| SQLAlchemy 2.0 | ORM | 2.0 风格的 `Mapped[]` 类型注解，IDE 和 mypy 能正确推断 |
| aiomysql | MySQL 异步驱动 | 与 SQLAlchemy 异步 API 配合 |
| Pydantic V2 | 数据校验 | 性能比 V1 快 5-50 倍，`model_validator` 支持跨字段校验 |
| pydantic-settings | 配置管理 | 类型安全的配置，缺失必填项时启动即失败 |
| Redis 5.2 | 缓存 + 分布式锁 | `SET NX EX` 原子加锁，`SCAN` 非阻塞遍历 |
| APScheduler | 定时任务 | `AsyncIOScheduler` 与 asyncio 事件循环集成 |
| passlib + bcrypt | 密码哈希 | bcrypt 自带盐、可调 cost，抗暴力破解 |
| pytest | 测试 | 99 个单元测试覆盖核心逻辑 |

### 前端

| 技术 | 用途 |
|------|------|
| Vue 3.5 (Composition API) | 框架，全部使用 `<script setup>` |
| Vue Router 4 | 路由，含路由级懒加载 + 声明式鉴权守卫 |
| Element Plus | UI 组件库，按需自动导入 |
| ECharts 5 | 数据可视化（按需引入，不是全量） |
| Vite 6 | 构建工具，含开发代理和手动分包 |
| axios | HTTP 客户端，含统一拦截器 |

**前端刻意没有引入 Pinia / Vuex** —— 全局共享状态只有"当前用户"一项，
用一个 `reactive` 对象 + 若干函数就够了。这是"按需引入复杂度"的取舍。

## 四、架构设计

### 后端三层架构

```
   HTTP 请求
      ↓
┌─────────────────┐
│   routers/      │  只做三件事：解析参数、调用 service、包装响应
│   （API 层）    │  不写任何业务判断
└────────┬────────┘
         ↓
┌─────────────────┐
│   services/     │  业务逻辑所在地
│  （业务层）     │  · 业务规则校验（状态机、权限、冲突检测）
                 │  · 事务边界控制（一个业务操作 = 一个事务）
                 │  · 缓存失效时机
                 │  · 调用外部服务（邮件）
└────────┬────────┘
         ↓
┌─────────────────┐
│ repositories/   │  只负责数据访问（SQL）
│  （数据层）     │  · 只增删改查，不含业务判断
                 │  · 不 commit（事务由 service 控制）
                 │  · 可以脱离业务单独测试
└────────┬────────┘
         ↓
      MySQL
```

**为什么要这样分层？** 

> "分层的目的不是'看起来规范'，而是让**每一层可以独立变化和测试**。
> 比如我要换掉 MySQL 换成 PostgreSQL，只需要改 repository 层，
> service 里的业务规则一行都不用动。
> 再比如我要测'预约冲突检测'这个业务规则，
> 可以脱离 HTTP 直接调 service，甚至传一个内存数据库。"

### 前端数据流

```
   组件（View）
      ↓ 调用
   composables（usePagination）    ← 封装重复逻辑
      ↓ 调用
   api/*.js（接口定义）            ← 只描述接口，一行一个
      ↓ 使用
   api/http.js（axios 实例）       ← 拦截器统一处理
      · 请求：自动带 Token
      · 响应：自动解包 data、统一错误提示、401 自动跳登录
      ↓
   后端 API
```

**关键设计：拦截器收拢所有横切关注点**

原项目的问题是每个 API 调用处各自处理错误、各自弹窗、各自判断 401。
V2 把"带 Token、解包、错误提示、登录过期跳转"这四件事全部收进拦截器，
业务代码里就只剩一行 `return http.get('/equipment')`。

## 五、初版有哪些问题、V2 怎么修的

这是本项目最有价值的部分 —— **每一个修复都对应一个真实的技术点**。

| # | 初版的问题 | 后果 | V2 的修复 | 涉及的技术点 |
|---|-----------|------|----------|-------------|
| 1 | 建库 SQL 漏了 `booking_count` 字段 | 统计接口 500；定时任务每次执行都回滚 | 用 ORM 的 `create_all` 建表，从根上消除脚本与模型不一致 | 单一事实来源 |
| 2 | 收藏接口参数拼错 `alise=`（应为 `alias`） | 收藏/取消收藏全部 422 | 修正为标准的 `Query(...)` | FastAPI 参数别名 |
| 3 | 管理端查询全部预约**没有任何鉴权** | 任何人不带 Token 就能拿到全平台预约数据 | 加 `Depends(require_admin)` | 越权访问、声明式权限 |
| 4 | 邮件用 `asyncio.create_task` 复用请求级数据库会话 | 会话关闭后后台任务报错，邮件时好时坏 | 请求内组装纯数据，后台不碰数据库；同步 smtplib 丢线程池 | 上下文生命周期、ORM detached |
| 5 | 图片只查扩展名、文件名用设备 ID | 改扩展名可上传可执行文件；换格式残留垃圾文件 | 读文件头判断真实类型 + UUID 文件名 + 按年月分目录 | 文件上传安全、路径穿越 |
| 6 | 前端要"猜"图片路径（三处三种拼法） | 有的地方 404，有的靠赌 `.png` | 后端统一转成完整路径，前端只有一个展示组件 | 契约设计、单一转换点 |
| 7 | 权限判断硬编码 `role.id == 2`，在 11 个路由复制粘贴 | 角色表重建就全错；改规则要改 11 处 | 抽成 `Depends(require_roles(...))` 工厂函数 | 依赖注入、DRY |
| 8 | `is_admin` 恒为 `false` | 前端判断管理员身份失效 | 响应模型里统一计算 | DTO 转换 |
| 9 | Windows GBK 下 emoji 日志导致启动崩溃 | 后端**根本起不来** | 入口处强制 UTF-8 输出 | 编码问题、跨平台 |
| 10 | **预约并发会重复**（check-then-act） | 同一设备同一时段被预约多次 | Redis 锁 + 数据库行锁 + **当前读** | **并发控制、事务隔离级别** |
| 11 | 静态文件用相对路径 | 换启动目录就写错位置 | 基于 `__file__` 推导绝对路径 | 路径可移植性 |
| 12 | "活跃用户"用 Token 未过期统计 | 指标口径错误，数据无意义 | 加 `last_used_at`，按真实访问行为统计 | 指标定义 |

**其中第 10 项值得单独说** —— 那是一个完整的 bug 定位过程：

1. 发现 8 个并发请求产生了 8 条重复预约
2. 验证 Redis 锁本身没问题（用最小实验证明互斥生效）
3. 用"反证法"确认 service 确实在加锁
4. 加数据库行锁 → 仍然重复
5. 写最小可复现实验（3 个并发事务），发现**行锁串行化成功但查冲突返回 0**
6. 定位到根因：**MySQL REPEATABLE READ 的快照读** —— 认证环节查用户时就固定了读视图
7. 解法：把冲突查询改成"当前读"（`with_for_update()`）
8. 验证：10 个并发只成功 1 个

详细过程见 `docs/第3批-预约模块与并发控制-设计说明.md`。

## 六、核心业务逻辑

### 预约状态机

```
                    ┌──────────────┐
   用户提交 ────────►│   pending    │
                    │   待审核     │
                    └──┬────┬───┬──┘
         管理员通过    │    │   │   用户取消
                       ▼    │   ▼
              ┌──────────┐  │  ┌───────────┐
              │ approved │  │  │ cancelled │
              │  已通过  │  │  │  已取消   │
              └────┬─────┘  │  └───────────┘
      定时任务检测 │        │ 管理员拒绝
      预约已结束   ▼        ▼
              ┌──────────┐ ┌──────────┐
              │completed │ │ rejected │
              │ 已完成   │ │  已拒绝  │
              └──────────┘ └──────────┘
```

状态流转规则集中定义在 `app/core/enums.py` 的一张表里，
**这是"状态怎么变"的唯一事实来源**。这样改规则不会漏，
而且测试可以直接对着表验证（本项目有 3 个测试专门验证状态机）。

### 时间冲突检测

核心公式只有一行：

```python
重叠 = end1 > start2 and start1 < end2
```

它是「不重叠」的补集（不重叠只有两种情况：A 在 B 之前结束、A 在 B 之后开始）。
比枚举 4 种重叠场景更不容易漏，而且**天然对称**。

时间语义是**左闭右开**：预约 9:00-11:00 占用 `[9:00, 11:00)`，
所以 9:00-11:00 和 11:00-13:00 **不冲突**（首尾相接）。

### 并发控制（三层防护）

| 层次 | 手段 | 作用 |
|------|------|------|
| 第 1 层 | Redis 分布式锁（按用户维度） | 快速失败、减少数据库锁竞争、串行化同一用户的请求 |
| 第 2 层 | 数据库行锁 `SELECT ... FOR UPDATE` | 保证正确性（**即使 Redis 挂了也有效**） |
| 第 3 层 | 冲突查询用"当前读" | 绕过 REPEATABLE READ 快照，读到最新已提交数据 |
| 兜底 | 数据库唯一约束 | 极端情况下的最后防线 |

**"用强一致的存储做最终保证，用弱一致的组件做性能优化"** ——
这是这个设计的核心思想，也是面试可以讲的重点。

### 缓存策略

| 数据 | 是否缓存 | TTL | 理由 |
|------|---------|-----|------|
| 设备分类 | ✅ | 2 小时 | 几个月才改一次，极其稳定 |
| 实验室列表 | ✅ | 2 小时 | 同上 |
| 设备详情（稳定字段） | ✅ | 30 分钟 | 名称/型号/图片变化少 |
| 设备详情（status/预约数） | ❌ | — | 变化频繁，每次实时查 |
| **设备列表** | ❌ | — | **筛选条件组合太多，缓存命中率极低** |

最后一条是初版的教训：初版给列表也做了缓存，
结果写入后很快被清空，**缓存从未命中过**，纯属浪费内存。
V2 直接去掉，并在代码注释里说明了原因。

## 八、开发建议

### 数据库改动

**不要手写 SQL 脚本**。改 `app/models/` 里的模型，然后：

```powershell
.venv\Scripts\python.exe scripts\init_db.py --drop   # 重建（会清空数据）
```

这样能保证表结构和模型定义永远一致。

> 生产环境的正确做法是引入 Alembic 做迁移（保留数据），
> 但本项目是教学项目，重建更简单直观。

### 加一个新接口

1. `schemas/xxx.py` 定义请求/响应模型
2. `repositories/xxx.py` 写数据访问
3. `services/xxx_service.py` 写业务逻辑
4. `api/routes/xxx.py` 写路由（只做参数解析和响应包装）
5. `api/router.py` 注册路由

### 环境变量

所有配置在 `backend/.env`，模板见 `backend/.env.example`。
**`.env` 已被 gitignore 排除**，不会泄露密码。

生产环境必须修改：
- `SECRET_KEY`：用 `python -c "import secrets; print(secrets.token_urlsafe(48))"` 生成
- `DEBUG=false`：关闭调试信息泄露
- `RATE_LIMIT_ENABLED=true`：开启限流
- `CORS_ORIGINS`：改成真实前端域名（不要用 `*`）

### 前端页面空白

按 `F12` 打开开发者工具看 Console。常见原因：
- 后端没启动（Network 里所有 `/api` 请求失败）
- 端口 5173 被旧项目占用（见 `3-启动前端.bat` 的提示）

### 端口被占用

```powershell
# 查占用进程
netstat -ano | findstr :8001
# 结束进程（把 PID 换成实际值）
taskkill /F /PID <PID>
```

### 想让 V1 和 V2 同时运行

- 后端：V1 用 8000，V2 用 8001 ✅ 已隔离
- 前端：V1 和 V2 都想用 5173 会冲突。
  修改 `frontend/vite.config.js` 里的 `server.port` 换个端口即可
- Redis：V1 用 db=0，V2 用 db=1 ✅ 已隔离
  （**这个必须隔离**，否则会互相读到对方的缓存）

## 十、面试准备

`docs/` 目录下的四份设计说明，每份末尾都有 **10-12 个自测问题**。
建议按这个顺序准备：

1. **先讲整体架构**：三层分层的理由、前后端契约设计
2. **重点讲并发控制**（第 3 批）—— 这是最有含金量的部分，
   因为它有真实的失败现象、系统的排查过程、可迁移的结论
3. **讲图片上传安全**（第 1、2 批）—— 文件头校验、路径穿越
4. **讲缓存取舍**（第 2 批）—— 为什么列表不缓存、初版错在哪
5. **讲认证方案选型**（第 2 批）—— UUID Token vs JWT 的取舍

**最重要的一点**：能主动说出方案的**局限**比吹嘘方案更值钱。
比如：

> "我的限流是内存实现，只在单进程下正确。
> 如果部署多 worker，每个进程各有自己的令牌桶，
> 实际放行量会是配置值的 N 倍。生产环境应该用 Redis 实现，
> 或者交给 API 网关。"

这种回答展示的是"知道自己方案的边界"，是初级和中级工程师的重要分水岭。
