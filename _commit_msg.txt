第3批：预约模块、并发控制、定时任务与邮件通知

并发控制（本批核心，含一次完整的 bug 定位过程）：
- Redis 分布式锁：SET NX EX 原子加锁 + Lua 脚本校验持有者后释放
- 数据库行锁：SELECT ... FOR UPDATE 锁住设备记录
- 关键修复：冲突查询改用【当前读】（with_for_update）
  根因是 MySQL REPEATABLE READ 的快照读特性 —— 认证环节查用户时
  读视图就已固定，导致拿到锁后查冲突仍读到旧快照，检测失效。
  用三个并发事务的最小实验做对比验证：快照读产生 3 条重复数据，
  改为当前读后只成功 1 条。
- 端到端验证：10 个并发 HTTP 请求只成功 1 个，无重复预约

预约业务：
- 区间重叠算法用补集写法（end1>start2 AND start1<end2），一行覆盖全部场景
- 左闭右开语义：首尾相接不算冲突（测试用例专门覆盖该边界）
- 状态机集中定义在 enums，五个状态流转可验证
- 资源级权限校验（防 IDOR 越权查看他人预约）
- 冲突预检接口用只读查询，不加锁，避免阻塞其他用户

定时任务：
- 设备状态同步：正向处理 approved 预约 + 反向兜底扫描脏状态
- is_counted 幂等标记，已验证重复执行不会重复累加
- APScheduler 配置 + 分布式锁防止多实例并发执行同一任务

邮件通知（修复原项目的真实 bug）：
- 原项目用 asyncio.create_task 复用请求级数据库会话，
  会话关闭后后台任务执行会报错，表现为邮件时好时坏
- V2 改为在请求内组装纯数据，后台任务完全不碰数据库
- 同步 smtplib 调用用 run_in_threadpool 跑在线程池，不阻塞事件循环

其他修复：
- 去掉设备维护中不能预约未来时段的错误检查（维护状态是临时的）
- 新增 RATE_LIMIT_ENABLED 开关，避免测试被限流拦截而得到假通过
- 种子数据扩充到 22 条，覆盖全部 5 种预约状态

测试：
- 99 个单元测试通过（含 44 个冲突算法与状态机用例）
- 11 组接口验证 + 定时任务幂等性验证通过
