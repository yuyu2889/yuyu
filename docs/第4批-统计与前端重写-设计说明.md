## 二、后端：统计模块的设计要点

### 1. "活跃用户"的准确定义（一个值得讲的指标口径问题）

原项目的"活跃用户"是这样算的：

```python
WHERE expires_at >= 30天前 AND is_revoked = 0
```

这实际上是 **"Token 还没过期的用户数"**，不是"活跃用户"。
而且因为本项目 Token 有效期是 7 天，"30 天内过期"就等于"所有当前有效的 Token" ——
**这个指标和"近 30 天活跃"毫无关系**，数据看板上显示的数字是误导性的。

V2 的修复：

1. `user_tokens` 表加 `last_used_at` 字段
2. 每次认证成功时更新它（带节流，同一分钟只写一次）
3. 统计时按 `last_used_at >= 30天前` 计算

**这个问题在面试里值得讲**：它体现的不是"技术难度"，而是
**"指标定义必须与业务含义一致"** 的产品意识。
很多项目的数据看板都有这类"看起来有数据、实际口径错了"的问题。

**顺带修的一个 bug**：实现 `last_used_at` 时我第一版只改了内存对象没有 commit，
导致数据库里一直是 `NULL`，统计出来永远是 0。
这说明"只改内存不提交"这类错误在 ORM 里很容易发生 —— 后来加上了节流提交。

### 2. 用 CASE WHEN 做条件聚合

```python
def _count_if(condition):
    """生成 SUM(CASE WHEN condition THEN 1 ELSE 0 END)"""
    return func.sum(case((condition, 1), else_=0))

# 一次查询算出多个指标
stmt = select(
    func.count(User.id).label("total"),
    _count_if(User.status == "active").label("active"),
    _count_if(User.status == "disabled").label("disabled"),
    _count_if(User.created_at >= week_ago).label("new_7d"),
)
```

**为什么不用 MySQL 的 `IF()` 函数？**
因为那是 MySQL 专有语法，换成 PostgreSQL/SQLite 就跑不了。
标准 SQL 的 `CASE WHEN` 更通用。

### 3. 7 天趋势：一次查询 vs 循环 7 次

原项目的做法是"循环 7 天，每天发一条 COUNT 查询"，也就是 **7 次数据库往返**。

V2 用 `GROUP BY 日期` 一次查回来，缺的日期在 Python 侧补 0：

```python
stmt = select(date_col, func.count(Booking.id)).where(...).group_by(date_col)
rows = await self.db.execute(stmt)

# 生成连续日期并补 0（折线图必须连续，不能断）
for i in range(days):
    current = start_date + timedelta(days=i)
    daily.append({"date": key, "booking_count": count_map.get(key, 0)})
```

**这是"把循环计算下推到数据库"的典型优化。**

另外这里用 `cast(Booking.created_at, Date)` 而不是 MySQL 的 `DATE()` 函数，
同样是出于跨数据库兼容的考虑。

### 4. 缺失状态要补 0

设备状态分布用于饼图。如果数据库里没有 `busy` 状态的设备，
`GROUP BY` 的结果里就不会有这一行，前端饼图就会**少一块**，看起来不对劲。

所以要在 Python 侧补齐所有预定义状态：

```python
counts = {status: 0 for status in EQUIPMENT_STATUS_NAMES}  # 先全部填 0
for status, count in rows:
    counts[status] = counts.get(status, 0) + count
```

### 5. 聚合接口（BFF 模式）

原项目首页要发 **5 个请求**才能凑齐数据：
用户信息、待审核数、收藏数、周预约数、可用设备数。

V2 用一个 `/statistics/dashboard` 接口一次返回全部。
为什么这很重要？

- 浏览器对同域名的并发请求数有限制（HTTP/1.1 下是 6 个）
- 每个请求都有 TCP/TLS 开销（虽然 keep-alive 能复用，但仍有头部开销）
- 5 个串行请求的延迟是 5 倍

**减少网络往返是前端性能优化最有效的手段之一。**

### 6. 权限隔离

统计接口分两类：

| 接口 | 权限 | 理由 |
|------|------|------|
| `/statistics/dashboard` | 登录 | 但普通用户拿到的全局字段是 0 |
| `/statistics/my/summary` | 登录 | 只有自己的数据 |
| `/statistics/users` | 管理员 | 涉及全平台用户规模 |
| `/statistics/equipment` | 管理员 | 设备排行属于运营数据 |
| `/statistics/bookings*` | 管理员 | 全平台预约数据 |

注意 `dashboard` 的处理方式：**同一个接口，按角色返回不同内容**，
而不是让前端调两个接口。这样前端只需要一处逻辑。

## 三、前端：架构设计

### 1. 为什么不用 Pinia？

这个项目全局共享的状态**只有"当前登录用户"一项**。

引入 Pinia 的代价：
- 多一个依赖
- 多一层间接（改状态要走 action）
- 多一个需要学习的概念

而用 `reactive` + 若干函数完全够用，且逻辑一眼看得懂、调试简单：

```javascript
const state = reactive({ token: '', user: null })

export function useAuthStore() {
  return { state, isLoggedIn, isAdmin, login, logout, ... }
}
```

**这是"按需引入复杂度"的取舍 —— 不是 Pinia 不好，
而是"为了一个用户对象引入整个状态管理库"不划算。**
如果将来状态变多（多标签页数据、复杂表单草稿），再迁移到 Pinia 也不迟。

**面试可以这样答**："我没有为了用而用，而是根据实际状态规模做了取舍，
并且说明了将来什么情况下会引入。"

### 2. 请求层：拦截器收拢横切关注点

原项目的问题：每个 API 调用处各自处理错误、各自弹窗、各自判断 401。

V2 的做法是把这四件事全部收进拦截器：

```javascript
// 请求拦截器：自动带 Token
http.interceptors.request.use((config) => {
  const token = localStorage.getItem(STORAGE_KEYS.TOKEN)
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 响应拦截器：解包 + 统一错误处理
http.interceptors.response.use(
  (response) => {
    const body = response.data
    if (body.code === ERROR_CODE.SUCCESS) {
      return body.data          // ← 业务代码不用再写 res.data.data
    }
    showErrorOnce(body.message)
    return Promise.reject(new Error(body.message))
  },
  (error) => {
    // 按 HTTP 状态码分类处理
    switch (error.response.status) {
      case 401: handleUnauthorized(); break   // 清登录态 + 跳登录页
      case 403: showErrorOnce('权限不足'); break
      ...
    }
  },
)
```

**两个细节值得讲**：

1. **错误提示要防重复**。页面初始化时并发 5 个请求，
   如果 Token 过期，5 个都返回 401 —— 不做处理会同时冒出 5 个弹窗。
   解法是用时间戳节流，同类错误 2 秒内只提示一次。

2. **401 跳转也要防重复**。同样用 `isRedirecting` 标记，
   并带上 `redirect` 参数，登录后能回到原来在看的页面。

### 3. usePagination：消除 7 份重复代码

原项目 7 个列表页各自重复写这一套：

```javascript
const list = ref([]); const total = ref(0)
const page = ref(1); const pageSize = ref(10); const loading = ref(false)
const fetch = async () => { loading.value = true; try {...} finally { loading.value = false } }
const handlePageChange = (p) => { page.value = p; fetch() }
// ... 还有 sizeChange、refresh、筛选联动
```

V2 封装成组合式函数后，页面里只需要：

```javascript
const { list, total, loading, pagination, refresh, handlePageChange } =
  usePagination(equipmentApi.listEquipments, { filters, pageSize: 12 })
```

**关键设计：筛选条件自动联动**。传入的 `filters` 是响应式的，
用 `watch(filters, ..., { deep: true })` 自动监听变化并重新查询，
还加了 300ms 防抖（避免用户每敲一个字都发请求）。

### 4. 设计令牌：换肤成本接近零

`styles/tokens.css` 里定义了所有颜色、间距、圆角、阴影、字号：

```css
:root {
  --color-primary: #409eff;
  --space-4: 16px;
  --radius-md: 8px;
  --shadow-md: 0 2px 8px rgba(0, 0, 0, 0.06);
  --font-base: 14px;
  /* ... */
}

/* 深色主题只覆盖变量，不改任何组件代码 */
html[data-theme='dark'] {
  --color-bg-page: #111827;
  --color-bg-card: #1f2937;
  --color-text-primary: #e5e7eb;
  /* ... */
}
```

**三个收益**：
1. **换肤只需改变量**，组件代码一行不用动（`data-theme` 属性切换）
2. **一致性**：不会出现"同一个颜色三种写法"（原项目就有这个问题）
3. **可维护**：要整体调大圆角，改一个变量

还顺便把 Element Plus 的主题变量也指到我们自己的令牌上，
这样组件库样式和自定义样式自动统一：

```css
:root {
  --el-color-primary: var(--color-primary);
  --el-color-success: var(--color-success);
  --el-border-radius-base: var(--radius-md);
}
```

### 5. 菜单由路由表生成

原项目的侧边栏菜单是手写的一堆 `<el-menu-item>`，
每加一个页面就要改一次菜单，而且容易和路由不一致。

V2 从 `router.options.routes` 自动生成：

```javascript
const menuItems = computed(() => {
  const children = router.options.routes.find(r => r.path === '/')?.children || []
  return children
    .filter(child => {
      if (child.meta?.hidden) return false                        // 详情页不进菜单
      if (child.meta?.requiresAdmin && !auth.isAdmin.value) return false  // 权限过滤
      return true
    })
    .map(child => ({ path: ..., title: child.meta.title, icon: child.meta.icon }))
})
```

好处：**只会多不会少** —— 路由加了菜单自动就有，不可能出现"页面存在但菜单里没有"。

### 6. 路由守卫：声明式鉴权

```javascript
{
  path: 'admin/users',
  meta: { title: '用户管理', requiresAdmin: true },   // ← 声明权限要求
}
```

守卫统一处理，不用在每个页面组件里写 if 判断。
这和后端的 `require_admin` 依赖是**同一个思路：声明式优于命令式**。

**但必须强调一点**（面试常问）：

> 前端的权限判断只是**体验优化**，不是安全措施。
> 因为 localStorage 里的用户信息用户自己可以改
> （打开开发者工具改成 `is_admin: true` 就能进管理页面的 UI）。
> 但他进去之后**所有管理接口都会被后端 403 拒绝**。
> **安全边界必须由后端守住**，这是基本原则。

### 7. EquipmentImage：图片处理的唯一出口

这是相对原项目最重要的一处简化。

原项目数据库存相对路径 `equipment/1.jpg`，前端在**三个地方**用了**三种**解析方式：
1. `helpers.js` 拼 `${API_BASE}/static/${image}`
2. `Admin.vue` 用正则抠扩展名，重组成 `${API_BASE}/static/equipment/${id}.${ext}`
3. `EquipmentManagement.vue` 直接把 image 当 src（结果 404）

V2 的原则：**后端返回可直接使用的路径，前端只有一个展示组件，逻辑只有三种情况**：

```
无图            → 渐变占位卡片（配色由设备名哈希决定，同名同色）
有图但加载失败  → 同样显示占位卡片（onerror 兜底）
有图            → 正常显示
```

**不做任何路径拼接或文件名推断。**

### 8. 深色模式的 FOUC 问题

FOUC = Flash of Unstyled Content（无样式内容闪烁）。

如果主题初始化放在 `onMounted` 里，会出现"先渲染浅色，再闪一下变深色"。
所以必须在**挂载前**执行：

```javascript
// main.js
useTheme().initTheme()   // ← 在 createApp 之前调用
const app = createApp(App)
```

这个小细节很能体现对渲染流程的理解。

### 9. ECharts 的三个实践要点

```javascript
// 1. 按需引入（而不是 import * as echarts）
import * as echarts from 'echarts/core'
import { BarChart, LineChart, PieChart } from 'echarts/charts'
import { GridComponent, TooltipComponent, ... } from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'
echarts.use([BarChart, LineChart, PieChart, GridComponent, ...])
```

全量引入会把整个库（约 1MB）打进 bundle，按需引入能减少一大半
（本项目实测 echarts chunk 是 522KB / gzip 176KB）。

```javascript
// 2. 图表实例必须销毁，否则内存泄漏
onUnmounted(() => {
  Object.values(charts).forEach(chart => chart?.dispose())
})

// 3. 窗口 resize 时要调 chart.resize()，否则显示错位
window.addEventListener('resize', handleResize)
```

**另外一个坑**：ECharts 的图表颜色不跟随 CSS 变量，
所以主题切换时需要重新 `setOption` 把文字颜色换成合适的值。
这是一个"设计令牌方案覆盖不到的地方"，需要单独处理。

### 10. 构建优化：手动分包

```javascript
// vite.config.js
rollupOptions: {
  output: {
    manualChunks: {
      'vue-vendor': ['vue', 'vue-router'],
      'element-plus': ['element-plus', '@element-plus/icons-vue'],
      echarts: ['echarts'],
    },
  },
}
```

**为什么？** 把体积大且不常变的库单独打成 chunk，
这样业务代码更新时，用户不需要重新下载这些库（利用浏览器缓存）。

配合路由级懒加载（每个页面一个 chunk），最终构建产物：

```
echarts-D9FixT80.js        522 KB (gzip 176 KB)   ← 只在统计页加载
element-plus-*.js        1,089 KB (gzip 342 KB)   ← 被缓存后不再重复下载
vue-vendor-*.js            108 KB (gzip  42 KB)
index-*.js                 68 KB (gzip  27 KB)    ← 应用主逻辑
各页面 chunk               1-13 KB 各自独立
```

## 四、本批踩坑记录

| # | 问题 | 根因 | 解决 |
|---|------|------|------|
| 1 | `last_used_at` 永远是 NULL | 只改内存对象没 commit | 加节流提交（同一分钟只写一次） |
| 2 | 测试脚本把"活跃用户"标签打成了"启用用户" | 测试代码字段映射写错 | 修正标签 |
| 3 | Dashboard 组件失效 | 混用了 `<script setup>` 和 Options API | 统一为 Composition API |
| 4 | Dashboard 的 style 块被脚本误删 | PowerShell 字符串截取时算错了位置 | 补回样式块 |
| 5 | 前端访问到的是 V1 项目 | V1 前端占着 IPv6 的 5173，`localhost` 解析到 IPv6 | 用 `127.0.0.1` 明确指定 |
| 6 | 图片 404 | 我猜的文件名不对（占位图用序列号，真实照片用哈希） | 查数据库确认真实路径 |

**第 3 个坑值得说一下**：一个 `.vue` 文件里同时出现 `<script setup>` 和 `<script>`（Options API）
是**合法但不推荐**的写法 —— Vue 支持两个 script 块共存（用于声明 options 如 `name`、`inheritAttrs`），
但把 `computed` 写在 Options API 里、又在 setup 里用，就会失效。
统一用 Composition API 更清晰。

**第 5 个坑也很有代表性**：
`localhost` 在 Windows 上可能解析成 IPv6 的 `::1`，
而不同程序监听的地址族不同，就会"明明服务起着却访问到别的东西"。
**排查这类问题时，用具体 IP 而不是 localhost，能减少一层不确定性。**

## 五、怎么运行

```powershell
# 后端（端口 8001）
cd backend
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001

# 前端（端口 5173）
cd frontend
npm run dev
```

浏览器打开 <http://127.0.0.1:5173>

**前后端联调说明**：前端代码里写的是相对路径 `/api/v1/...`，
由 Vite 的 dev proxy 转发到 `http://127.0.0.1:8001`（配置在 `vite.config.js`）。

这样做的好处是**不硬编码后端地址** —— 换环境（本地/测试/生产）时
不需要改代码，只改 Vite 配置或 Nginx 配置即可。

**面试最有价值的三块**：
1. **并发控制**（第 3 批）—— 有完整的问题定位过程，涉及数据库隔离级别
2. **图片上传安全**（第 1、2 批）—— 文件头校验 + 路径穿越防护
3. **缓存取舍**（第 2 批）—— 能讲清"为什么某处不缓存"比"我用了缓存"更有价值

最后再强调一次那份设计文档里的话：

> **能主动说出方案的局限，比吹嘘方案更值钱。**
> 面试官想找的不是"什么都会的人"，而是"知道自己方案边界在哪里的人"。
