## 二、核心设计决策（面试重点）

### 1. 为什么用 `{code, message, data}` 统一响应？

你原项目最大的接口问题就是**格式不统一**：正常业务返回 `{code, message, data}`，
但 FastAPI 的参数校验失败返回 `{detail: [...]}`，前端得写两套解析逻辑。

V2 的做法是注册 6 个异常处理器，把所有出口收拢：

```python
app.add_exception_handler(AppException, ...)             # 自己的业务异常
app.add_exception_handler(RequestValidationError, ...)   # 参数校验（关键！）
app.add_exception_handler(StarletteHTTPException, ...)   # 404/405 等
app.add_exception_handler(IntegrityError, ...)           # 数据库约束
app.add_exception_handler(SQLAlchemyError, ...)          # 其他数据库错误
app.add_exception_handler(Exception, ...)                # 兜底
```

**分层思考**：HTTP 状态码表达传输层语义，业务码表达业务原因。
两者都要，但职责不同 —— 只靠 HTTP 码无法区分「用户不存在」和「密码错误」。

**安全点**：`DEBUG=false` 时，响应里绝不返回 traceback 和 SQL 错误。
你原项目把 traceback 直接返回给前端，是明确的信息泄露。

### 2. 图片模块：为什么这么改？（这是第 1 批的重点）

对照你原项目的四个问题：

| 原项目问题 | 后果 | V2 的做法 |
|---|---|---|
| 只查文件扩展名，不看内容 | 把 `evil.exe` 改名成 `evil.jpg` 就能传上来 | **读文件头（magic bytes）判断真实类型** |
| 文件名用 `{设备ID}.{扩展名}` | 换扩展名残留旧文件（你的 `6.png`/`8.png`） | **UUID 文件名**，永不冲突覆盖 |
| 所有文件平铺在一个目录 | 文件多了文件系统查找变慢 | **按年月分目录** `2026/10/` |
| 前端要"猜"文件名规则拼 URL | `Admin.vue` 里那段正则 + 赌 `.png` 的后备路径 | **数据库只存相对路径，前端统一拼接** |

**文件头校验的实现原理**（这段值得记住）：

```python
MAGIC_SIGNATURES = [
    (b"\xff\xd8\xff",          "image/jpeg", ".jpg"),   # JPEG
    (b"\x89PNG\r\n\x1a\n",     "image/png",  ".png"),   # PNG
    (b"GIF87a",                "image/gif",  ".gif"),   # GIF
    (b"GIF89a",                "image/gif",  ".gif"),
]
# WebP 特殊：前 4 字节 RIFF，第 8-11 字节 WEBP
```

文件的**前几个字节是固定魔数**，任何文件都伪造不了开头。
所以「读开头几个字节」比「看文件名后缀」可靠得多。

**路径穿越防护**（面试常考的 Web 安全问题）：

```python
candidate = (BASE_DIR / "app" / "static" / relative_path).resolve()
if not candidate.is_relative_to(UPLOAD_ROOT.resolve()):
    logger.error("拒绝删除越界路径")
    return False
```

如果不做这个校验，数据库里存的路径一旦被改成 `../../../Windows/System32/xxx`，
删除接口就会去删系统文件。这叫**路径穿越（Path Traversal）**漏洞。

**顺带讲一个设计好处**：因为所有文件操作都封装在 `FileStorageService` 里，
以后要迁移到阿里云 OSS / MinIO，**只需要换掉这一个类的实现，业务代码一行都不用改**。
这就是"把变化点封装起来"的价值——面试官问"你的代码怎么应对需求变化"，
这就是一个具体答案。

### 3. 密码为什么要用 bcrypt 而不是 SHA256？

- SHA256 是为「快」设计的，GPU 一秒能算几十亿次 → 暴力破解成本极低
- bcrypt 故意「慢」（可调 cost），单次约 100ms → 破解成本高几个数量级
- bcrypt **自带随机盐**，同一密码每次哈希结果都不同 → 彻底防彩虹表

**一个容易忽略的坑**：bcrypt 只取密码前 **72 字节**，超出部分静默忽略。
而且必须**按字节截断**，不能按字符 —— 一个中文占 3 字节，
所以中文密码超过 24 个字符就会被截断。见 `_truncate_password()`。

### 4. 配置管理：为什么要用 pydantic-settings？

对比两种写法：

```python
# 原项目：散落的 os.getenv
DB_PORT = int(os.getenv("DB_PORT", "3306"))        # 每次都要手动转类型
PASSWORD = os.getenv("DB_PASSWORD", "******")      # 密码硬编码成默认值（危险）
```

```python
# V2：类 + 类型注解
class DatabaseSettings(BaseSettings):
    port: int = Field(3306, alias="DB_PORT")       # 自动类型转换
    password: str = Field(..., alias="DB_PASSWORD") # 必填，缺失则启动失败
```

三个好处：
1. **类型安全**：`DB_PORT=abc` 启动就报错，而不是运行时崩
2. **启动即校验**：必填项缺失时应用直接起不来（快速失败），不用等出问题才发现
3. **集中管理**：所有配置一处可查，还带注释

**踩过的坑（值得记住）**：嵌套的 Settings 类**必须自己也声明 `env_file`**，
否则读不到 `.env`，只认系统环境变量。我在这里卡过一次。

### 5. 连接池的 `pool_pre_ping` 解决什么问题？

MySQL 默认 8 小时会主动断开空闲连接（`wait_timeout`）。
如果代码还握着这个已断开的连接去执行 SQL，就报 `MySQL server has gone away`。

两个应对措施：
- `pool_recycle=1800`：连接存活超过 30 分钟就主动回收重建
- `pool_pre_ping=True`：取连接前先 ping 一下，失效的丢弃

`pool_pre_ping` 是更省心的方案，代价是每次取连接多一次往返（约 0.1ms，可接受）。

### 6. `expire_on_commit=False` 是干什么的？

SQLAlchemy 默认 `expire_on_commit=True`：commit 后所有对象属性过期，
下次访问会触发新的 SELECT 去刷新。

在**异步**环境里这个隐式 IO 会直接抛 `MissingGreenlet` 错误
（因为它在同步上下文里尝试发异步查询）。

设为 `False` 后，commit 后对象仍可直接读取，避免这一类坑。

### 7. 令牌桶限流，以及它的局限（这点必须能讲）

**令牌桶算法**：桶有固定容量，以固定速率补令牌，每个请求消耗一个，
桶空则拒绝。相比"固定窗口计数"，它允许一定程度的突发流量。

**局限（面试官一定会追问）**：这个实现存在**进程内存**里，
只在**单进程**下正确。如果部署 `uvicorn --workers 4`，
每个进程各有自己的桶，实际放行量是配置值的 4 倍。

生产环境应该：
- 用 Redis 实现（`INCR` + `EXPIRE`，或用 Lua 脚本保证原子性）
- 或者交给 Nginx / API 网关

**能主动说出这个局限，比实现本身更加分。**

## 三、数据库设计的变化（对比原项目）

| 项 | 原项目 | V2 | 为什么改 |
|---|---|---|---|
| 审核信息 | 拼进 `notes` 字段：`【管理员xx审核备注：yy】` | 独立三列 `audited_by` / `audited_at` / `audit_note` | 原做法无法查询、无法统计"谁审的"，改格式要写字符串解析 |
| 权限判定 | 硬编码 `role.id == 2` | 用 `role.code == "admin"` | 角色表数据重建后 id 会变，硬编码就全错 |
| 建表方式 | 手写 `.sql` 脚本 | ORM 的 `create_all` | 原项目 SQL 脚本与模型不一致（脚本漏了 `booking_count`，导致定时任务每次失败） |
| 外键删除语义 | 数据库 `SET NULL` vs ORM `delete-orphan`（矛盾） | 统一为 `RESTRICT` | 两套相反语义必然出 bug |
| 字段长度 | 模型 `String(500)` vs 数据库 `TEXT`（不一致） | 统一 `Text` | 消除不一致 |
| 分页字段名 | 各接口不统一 | 统一 `PageData` 结构 | 前端只写一次分页逻辑 |

### 一个"设计权衡"案例：冗余统计字段

`equipment.browse_count` 和 `booking_count` 是**反范式设计**——
每次查设备都去 `COUNT` 一遍预约表成本太高，所以在设备表上冗余一个计数。

**代价**：必须保证它和真实数据一致。原项目靠定时任务在预约结束时 +1，
并用 `is_counted` 标记防重复计数（幂等）。

V2 保留这个设计，但把更新逻辑收敛到 service 层一处，
并且明确：**这是用一致性换查询性能的取舍**，不是随手加的字段。

## 四、踩坑记录（这些错误你也可能遇到）

| 报错 | 原因 | 解决 |
|---|---|---|
| `ValidationError: DB_USER Field required` | 嵌套的 `DatabaseSettings` 没声明 `env_file` | 子配置类也要写 `model_config = SettingsConfigDict(env_file=...)` |
| `AmbiguousForeignKeysError: Booking.user` | `bookings` 表有两个外键指向 `users`（预约人 + 审核人） | 每条通到 User 的关系都要显式写 `foreign_keys` |
| `TypeError: 'FieldInfo' object is not subscriptable` | `PageData` 里字段名叫 `list`，遮蔽了内置 `list` 类型 | 用 `typing.List[T]`，并把该字段放到类定义最后 |
| `Access denied for user 'yuyu' to database 'lab_booking_v2'` | 新建的库没给项目账号授权 | `GRANT ALL PRIVILEGES ON lab_booking_v2.* TO 'yuyu'@'127.0.0.1'` |
| `UnicodeEncodeError: 'gbk' codec` | Windows 控制台默认 GBK，日志含 emoji | 入口处 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |

## 六、下一批（第 2 批）会做什么

用户认证与权限 + 设备模块：

1. **认证**：登录/注册/登出、UUID Token 校验依赖、**滑动续期**、过期 Token 定时清理

4. **设备模块**：分类、列表（分页 + 筛选）、详情（浏览量自增 + Redis 缓存）、
   增删改（含图片上传完整流程）
5. **测试**：认证流程和图片校验的 pytest 用例
