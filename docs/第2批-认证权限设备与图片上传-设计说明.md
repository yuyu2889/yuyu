## 二、核心设计决策

### 1. 权限依赖为什么用「工厂函数」？（本批最重要的设计）

看你原项目的问题 —— 这段代码在 `routers/admin.py` 里**复制了 11 次**：

```python
# 原项目
is_admin = any(role.id == 2 for role in user.roles) if user.roles else False
if not is_admin:
    raise HTTPException(status_code=403, detail="权限不足")
```

复制 11 遍的后果：**想改权限规则要改 11 个地方，漏一个就是安全漏洞。**

V2 的解法是工厂函数：

```python
def require_roles(*role_codes: RoleCode) -> Callable:
    async def _checker(current_user: CurrentUser) -> User:
        if not ({c.value for c in role_codes} & set(current_user.role_codes)):
            raise PermissionError_(f"权限不足，需要：{...}")
        return current_user
    return _checker

require_admin = require_roles(RoleCode.ADMIN)
```

使用起来是**声明式**的，一眼能看出接口的访问级别：

```python
@router.delete("/equipment/{id}", dependencies=[Depends(require_admin)])
```

**为什么这比 `if` 判断好？**
1. 策略集中——改规则只改一处
2. 可审计——能扫一遍所有路由自动生成权限矩阵表
3. 可测试——权限逻辑能单独测，不用启动整个接口
4. 声明式——读代码时不用翻到函数体内部才知道谁能访问

### 2. 为什么选 UUID Token 而不是 JWT？（面试必问，背下来）

| 维度 | UUID Token（本项目） | JWT |
|------|---------------------|-----|
| 服务端存储 | 需要（一张表） | 不需要 |
| **即时撤销** | **改个字段就行** | **必须维护黑名单** |
| 滑动续期 | 更新过期时间即可 | 必须重新签发 |
| 每请求开销 | 一次数据库查询（走索引） | 纯计算，无 IO |
| 水平扩展 | 多实例共享同一张表 | 天然无状态 |

**本项目的选择理由**：有两个需求决定了必须能即时撤销：
1. 管理员禁用用户后要**立刻**踢下线
2. 改密码后**立刻**让旧 Token 失效

用 JWT 实现这两点反而更复杂（要引入黑名单 + Redis）。
代价是每次请求多一次数据库查询，但走的是唯一索引，开销很小。

**这个答案的加分点在于：你不是"随便选的"，而是被两个具体需求驱动的。**

### 3. 改密码后必须撤销所有 Token（很多人会漏）

```python
user.password = get_password_hash(data.new_password)
await self.token_repo.revoke_by_user_id(user.id)   # ← 这一行是关键
```

如果不做这一步：用户发现密码泄露 → 改了密码 → **但攻击者手里的 Token 还能用 7 天**。
改密码就失去意义了。

测试用例【16】验证了这一点：改完密码后用旧 Token 访问返回 401。

### 4. 防用户名枚举（安全细节）

```python
if user is None or not verify_password(data.password, user.password):
    raise AuthError(ErrorCode.PASSWORD_ERROR, "用户名或密码错误")
```

**用户不存在**和**密码错误**返回完全相同的提示。为什么？

如果区分，攻击者就能拿一个用户名字典去撞这个接口，
根据返回的是"用户不存在"还是"密码错误"，**枚举出系统里有哪些用户名**。
拿到用户名列表后，就可以针对性地做密码爆破或社会工程攻击。

测试用例【4】验证了两者提示完全一致。

### 5. 图片上传：三层安全防护

这是你原来最头疼的模块。V2 的完整防线：

**第一层：大小限制**（防 DoS）
```python
if len(content) > settings.max_upload_size_bytes:
    raise FileUploadError(ErrorCode.FILE_TOO_LARGE, f"文件大小 {actual_mb:.1f}MB 超出限制")
```

**第二层：读文件头判断真实类型**（防伪装）
```python
MAGIC_SIGNATURES = [
    (b"\xff\xd8\xff",      "image/jpeg", ".jpg"),   # JPEG
    (b"\x89PNG\r\n\x1a\n", "image/png",  ".png"),   # PNG
    (b"GIF87a",            "image/gif",  ".gif"),
    (b"GIF89a",            "image/gif",  ".gif"),
]
# WebP 特殊：第 0-3 字节 RIFF，第 8-11 字节 WEBP
```

**文件名可以随便改，但文件开头的几个字节改不了。** 这就是"读文件头"比"看扩展名"可靠的原因。

测试用例【12】实际构造了一个 Windows 可执行文件（`MZ` 头）命名为 `evil.jpg`，
结果被拒绝 —— 这验证了防护真的生效，而不是"理论上应该生效"。

**第三层：UUID 文件名 + 路径穿越防护**（防覆盖 + 防越权访问）
```python
stored_name = f"{uuid.uuid4().hex}{extension}"   # 不用用户提供的文件名
candidate = (BASE_DIR / "app" / "static" / relative_path).resolve()
if not candidate.is_relative_to(UPLOAD_ROOT.resolve()):
    return False   # 拒绝越界路径
```

如果不做 UUID 替换，用户传 `../../../../etc/passwd` 作为文件名就可能写到系统目录。
如果删除时不校验路径，数据库里的路径被篡改后就能删系统文件。

### 6. 图片路径的「单一转换点」——解决你原来的核心痛点

**你原来的问题**：数据库存 `equipment/1.jpg`，前端在三个地方用了三种解析方式：

```javascript
// helpers.js：简单拼接
`${API_BASE}/static/${equipment.image}`

// Admin.vue：用正则抠出扩展名，用设备ID重组文件名
const m = imagePath.split('?')[0].match(/\.(png|jpg|jpeg)$/i)
if (m) return `${API_BASE}/static/equipment/${equipmentId}.${m[1]}`
return `${API_BASE}/static/equipment/${equipmentId}.png`   // ← 猜不出来就赌 png

// EquipmentManagement.vue：直接把相对路径当 src（必然 404）
<el-image :src="row.image" />
```

**V2 的原则：字段自描述 + 后端统一转换**

```python
def to_static_url(relative_path: Optional[str]) -> Optional[str]:
    """三种情况：空→None；已是完整URL→原样返回；相对路径→加 /static/ 前缀"""
```

所有响应模型的 image 字段都经过 `field_validator` 调用它：

```python
class EquipmentResponse(ORMModel):
    image: Optional[str] = None

    @field_validator("image", mode="before")
    @classmethod
    def convert_image(cls, v):
        return to_static_url(v)
```

**这样做的收益**：
- 前端只需判断一种情况：为空就显示占位图
- 前端不需要知道任何文件名规则
- 后端换存储方案（本地 → 阿里云 OSS）对前端**完全透明**
- 因为写在响应模型上，"只要用了这个模型转换就一定发生"，不会漏

### 7. 列表查询用 DTO 投影而不是 ORM 对象

```python
rows, total = await self.equipment_repo.list_with_stats(...)
items = [EquipmentResponse(**row) for row in rows]
```

为什么返回 dict 而不是 ORM 对象？因为列表要带**聚合出来的字段**
（收藏数、当前有效预约数），ORM 对象上根本没这些属性。

附带好处：SQL 只 SELECT 需要的列，
不会把 `description`（TEXT，可能很长）这种用不到的字段也取回来。

### 8. 设备列表故意不缓存（重要的设计取舍）

```python
# equipment_service.list_equipments
# 说明：这个接口没有走缓存。
# 因为列表的筛选条件组合是笛卡尔积（关键词 × 分类 × 状态 × 排序 × 页码），
# 缓存命中率极低，反而会产生大量无效缓存占用内存。
```

**这正是你原项目"列表缓存写了从来没命中"问题的根治方案。**

正确的缓存对象是：**高频重复读取、且变化少的数据**
- ✅ 设备分类（几个月才改一次）
- ✅ 实验室列表
- ✅ 设备详情里的稳定字段（名称/型号/图片）
- ❌ 设备列表（条件组合太多）
- ❌ 设备状态、预约次数（变化太频繁）

### 9. 详情的缓存用「按字段易变性分层」

```python
# equipment_service.get_detail
# 每台设备的详情缓存只存稳定字段；
# status 和 booking_count 每次实时查库。
```

比"整个对象缓存"或"整个不缓存"更优 —— 这是**有意识的取舍**，不是偷懒。

### 10. 删除设备前必须检查有效预约

```python
active_count = await self.db.execute(
    select(func.count()).select_from(Booking).where(
        Booking.equipment_id == equipment_id,
        Booking.status.in_(["pending", "approved"]),
    )
)
if active_count > 0:
    raise ConflictError(..., f"该设备还有 {active_count} 条未完成的预约，请先处理")
```

**为什么不能直接删？** 删掉设备后，那些预约就变成了"指向不存在设备的孤儿记录"，
用户查看"我的预约"时会出错，统计也会失真。

生产环境更好的做法是**软删除**（加 `deleted_at` 字段，逻辑上标记删除但数据保留），
这样还能恢复。本项目采用硬删除 + 前置检查，在文档里说明了两者的取舍。

### 11. 统计字段用数据库端原子自增

```python
async def increment_browse_count(self, equipment_id: int) -> int:
    stmt = update(Equipment).where(Equipment.id == equipment_id) \
        .values(browse_count=Equipment.browse_count + 1)   # ← SQL 表达式
```

**不要写成**「查出来 +1 再写回去」：

```python
eq = await repo.get(id); eq.browse_count += 1   # ← 并发下会丢更新
```

并发场景：两个请求都读到 100，各自写回 101 —— 实际应该涨到 102，
**一次浏览量被丢掉了**。数据库端原子自增天然免疫这个问题。

## 四、本批踩坑记录（都是真实发生并修复的）

### 坑 1：`EmailStr` 需要额外依赖

```
ImportError: email-validator is not installed, run `pip install pydantic[email]`
```

Pydantic 的 `EmailStr` 不是开箱可用的，必须装 `email-validator`。
**这个报错发生在"模型定义阶段"（import 时），不是"使用时"** ——
所以症状是"服务根本起不来"，而不是"某个接口报错"，容易让人摸不着头脑。

### 坑 2：Redis 缓存库被两个项目共用（最隐蔽的一个）

**症状**：接口返回 8 个分类而且设备数全是 0，但直接查数据库明明是 6 个分类、有设备数。

**排查过程**：
1. 先查数据库 → 6 个分类，数据正确
2. 再查 Python 层（`repo.list_all()` / `count_equipments(1)`）→ 6 个分类，返回 7 ✅
3. 那问题只能出在**中间**：接口读的是缓存，而缓存里是旧数据

**根因**：V1（旧项目）和 V2 用**同一个 Redis 实例的同一个 db（0）**，
而且缓存键名都叫 `equipment:categories`。V2 读到 V1 写的缓存，
数据结构不同（V1 没存 `equipment_count` 字段），所以全是 0。

**修复**：V2 改用 `REDIS_DB=1`，两个项目彻底隔离。

**这个坑的普遍意义**：多个服务共用一个 Redis 时，
一定要做**命名空间隔离**（不同 db 号，或者 key 加业务前缀）。
否则会出现"数据莫名其妙不对"这种最难排查的问题。

### 坑 3：URL 里的中文没编码

```
UnicodeEncodeError: 'ascii' codec can't encode characters in position 30-32
```

用代码发请求时，`?keyword=示波器` 必须做百分号编码：

```python
from urllib.parse import quote
q = quote(q, safe="=&")     # 保留分隔符，只编码值
```

浏览器会自动帮你编码，所以这个坑只在"用代码发请求"时暴露。
但**后端也必须能正确解码**，这次测试顺便验证了 FastAPI 对中文查询参数的处理是正常的。
