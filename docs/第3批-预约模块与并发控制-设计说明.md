## 二、核心设计：并发控制（本批最重要）

### 1. 问题：check-then-act 竞态

朴素实现是这样的：

```python
conflicts = await check_conflict(...)   # 查有没有冲突
if conflicts:
    raise Error
await insert(...)                       # 没有就插入
```

两个并发请求会这样交错：

```
时刻    请求A                        请求B
t1      查询冲突 → 无
t2                                   查询冲突 → 无
t3      插入成功
t4                                   插入成功     ← 重复了！
```

两次检查都通过，但结果是重复预约。这叫 **TOCTOU 竞态**
（Time-Of-Check to Time-Of-Use）。

### 2. 我的第一版方案（错的，但过程值得记录）

我加了三层防护：

```
第 1 层  Redis 分布式锁（按用户维度）→ 串行化并发请求
第 2 层  事务内冲突检测（区间重叠算法）→ 业务正确性
第 3 层  数据库唯一约束兜底
```

**测试结果：8 个并发请求全部成功，产生了 8 条重复预约。** 三层防护全都没用。

### 3. 排查过程（这段经历本身就是面试素材）

**第 1 步：验证 Redis 锁是否真的互斥**

写了个最小实验：10 个并发任务抢同一把锁，各自做"读-改-写"：

```
计数器最终值: 10（无锁时通常小于 10，有锁时应为 10）
结论: 锁生效 ✓
```

锁本身没问题。

**第 2 步：反证法验证 service 是否真的在加锁**

方法：在调用 service 之前，我"手动抢住"它应该用的那把锁。
如果 service 真去加锁了，它就会因为拿不到锁而失败。

```
手动抢锁: True
service 调用结果: 被拒绝 ConflictError/CONFLICT
  您有另一个预约请求正在处理中，请稍后重试
[OK] 结论：service 确实会加锁，锁机制生效。
```

service 确实加锁了。那问题在哪？

**第 3 步：加数据库行锁（假设：Redis 锁不够，需要数据库锁）**

```python
await self.equipment_repo.lock_for_booking(data.equipment_id)  # SELECT ... FOR UPDATE
```

**结果：仍然 8 条重复。**

**第 4 步：最小可复现实验（决定性的一步）**

不再猜代码，直接写一个最底层的实验：3 个并发事务，
各自"认证查询 → 抢行锁 → 查冲突 → 插入"。

```
T0: 认证查询完成（读视图已建立）
T0: 获得行锁
T0: 查到冲突数 = 0
T2: 认证查询完成（读视图已建立）
T1: 认证查询完成（读视图已建立）
T2: 获得行锁          ← 注意：T2 能拿到锁，说明 T0 已经释放了
T0: 插入并提交成功
T2: 查到冲突数 = 0    ← 但 T2 看不到 T0 刚提交的数据！
T2: 插入并提交成功
T1: 获得行锁
T1: 查到冲突数 = 0
T1: 插入并提交成功
结果: ['success', 'success', 'success']
```

**这个日志把真相说清楚了**：

- ✅ 行锁**确实生效**了（三个事务依次获得锁，严格串行）
- ❌ 但每个事务查冲突时都返回 **0**，看不到前一个事务刚提交的数据

也就是说：**问题不在锁，而在"读到了旧数据"。**

**第 5 步：定位根因 —— MySQL 快照读**

MySQL 默认隔离级别是 `REPEATABLE READ`。它的规则是：

> 事务的「一致性读视图」在**第一次查询时**建立，
> 之后该事务里的普通 `SELECT` 都读这个快照，**看不到其他事务后来的提交**。

而一个 HTTP 请求的流程是：

```
1. 认证：SELECT * FROM users WHERE id=?   ← 读视图在这一刻就固定了！
2. 拿 Redis 锁
3. 拿数据库行锁
4. 查冲突  ← 普通 SELECT，读的是第 1 步的快照
5. 插入
```

所以即使第 3 步已经把请求串行化了，第 4 步依然看不到
"上一个请求在后面提交的数据" → 判定无冲突 → 重复预约。

### 4. 最终解法：把冲突查询也变成「当前读」

```python
stmt = (
    select(Booking)
    .where(and_(*conditions))
    .with_for_update()      # ★ 关键：当前读（current read）
)
```

`SELECT ... FOR UPDATE` 与普通 `SELECT` 的语义完全不同：

| | 普通 SELECT | SELECT ... FOR UPDATE |
|---|---|---|
| 读什么数据 | 事务开始时的快照 | **最新已提交数据** |
| 会不会加锁 | 不加锁 | 加行锁 + 间隙锁 |
| 术语 | 一致性读（consistent read） | 当前读（current read） |

**验证（同一实验，只改这一个地方）：**

| 冲突查询模式 | 3 个并发事务的结果 | 数据库记录数 |
|---|---|---|
| 快照读（不加 FOR UPDATE） | success, success, success | **3 条重复** ❌ |
| **当前读（加 FOR UPDATE）** | success, conflict, conflict | **1 条** ✅ |

**端到端验证（10 个并发 HTTP 请求）**：

```
成功数: 1  (期望 1)
  9 次 | HTTP 409 code=4003 | 您在该时段已有预约「混合域示波器」（14:00-16:00）
数据库实际预约数: 1  (期望 1)
>>> 并发控制正确：10 个并发只成功 1 个
```

### 5. 这个案例的面试讲法（建议背下来）

> "我做的预约系统需要防并发重复预约。我一开始用 Redis 分布式锁按用户维度串行化，
> 测试发现 8 个并发请求全部成功、产生了重复数据。
>
> 排查时我写了几个最小实验：先验证锁本身是互斥的，再用反证法确认 service
> 确实在加锁，然后加了数据库行锁 —— 都没解决。
>
> 最后我写了个最底层的三事务实验，看日志发现：行锁确实把事务串行化了，
> 但每个事务查冲突时都返回 0。这时我意识到问题不在锁，而在**读**：
> MySQL 的 REPEATABLE READ 下，事务的读视图在第一次查询时就固定了，
> 而认证环节要查用户表，那一刻快照就建好了 —— 所以后面即使串行执行，
> 读到的还是旧快照。
>
> 解法是把冲突查询从一致性读改成当前读（加 FOR UPDATE），
> 这样能读到最新已提交数据。改完后 10 个并发只成功 1 个。
>
> 这件事让我理解到：**在 REPEATABLE READ 下，'先查后插'这种模式
> 即使在应用层加了锁，也必须保证那个'查'是当前读**，
> 否则一致性快照会让检测失效。"

**为什么这个回答加分**：
1. 有具体的失败现象和数字，不是空谈
2. 展示了系统化的排查方法（最小实验、反证法、对比实验）
3. 触及了数据库隔离级别这个"进阶话题"
4. 结论可迁移（不只是修了一个 bug，而是总结出通用规律）

## 三、冲突检测算法

### 为什么用「补集」而不是「枚举」

两个时间区间重叠有 4 种情况（A 在前、A 在后、A 包含 B、A 被 B 包含），
穷举容易漏，还要小心边界。

换成补集思路，**不重叠只有两种情况**：

```
1. A 在 B 之前结束：  end1 <= start2
2. A 在 B 之后开始：  start1 >= end2
```

所以：

```python
重叠 = NOT (end1 <= start2 OR start1 >= end2)
     = end1 > start2 AND start1 < end2
```

一行搞定。好处：
- 不可能漏场景
- **天然对称**（overlap(A,B) == overlap(B,A)，测试里专门验证了这条性质）
- 边界语义正确：`end1 == start2` 时（首尾相接）判定为不冲突 ✓

### 边界语义：左闭右开

预约 9:00-11:00 占用 `[9:00, 11:00)`，所以：

| 场景 | 是否冲突 |
|------|---------|
| 9:00-11:00 vs 11:00-13:00 | **不冲突**（首尾相接） |
| 9:00-11:00 vs 10:00-12:00 | 冲突 |
| 9:00-11:00 vs 10:59-13:00 | 冲突（只重叠 1 分钟也算） |

**这个语义必须和业务确认清楚** —— 如果实验室要求"结束后要留 10 分钟整理"，
就需要改成 `end1 + 10min > start2`。测试用例里把这条边界单独列出来了。

### 为什么在 SQL 里过滤而不是 Python 循环

原项目在 SQL 里用 `str_to_date(concat(booking_date,' ',end_time))` 现场拼时间，
这有两个严重问题：

1. **函数作用于列 → 索引失效**。数据库无法使用
   `(equipment_id, booking_date, status)` 索引，只能全表扫描。
2. **数据库方言绑定**。`str_to_date` 是 MySQL 专有函数，换成 PostgreSQL 就跑不了。

V2 的做法：因为已经限定了"同一设备 + 同一天"，所以只需要比较 `time` 类型，
直接用两个不等式，索引能命中，且跨数据库通用。

## 四、状态机

五态流转集中定义在 `app/core/enums.py` 的一张表里：

```python
BOOKING_STATUS_TRANSITIONS = {
    PENDING:   {APPROVED, REJECTED, CANCELLED},
    APPROVED:  {COMPLETED, CANCELLED},
    REJECTED:  set(),      # 终态
    CANCELLED: set(),      # 终态
    COMPLETED: set(),      # 终态
}
```

**为什么集中定义？** 原项目的状态判断散落在各个路由的 `if` 里，
改规则要翻遍所有文件，且容易出现"A 处允许、B 处拒绝"的不一致。
集中成一张表后：
- 唯一事实来源，不会矛盾
- 能一眼看出哪些是终态
- 测试可以直接对着表验证（本项目 3 个测试专门验证状态机）

## 五、定时任务

### 为什么要"周期性扫描"而不是"到点触发"

"到点精确触发"需要延迟队列，实现复杂且**容易丢**（服务重启就丢了）。
用"每 60 秒扫描一次 + 状态比对"，即使服务停了一天，
重启后扫描一次就能把所有状态修正过来。

这种"不追求实时、只保证最终正确"的思路叫**最终一致性**。

### 幂等（idempotent）—— 定时任务的核心概念

定时任务每 60 秒跑一次，同一条数据会被**反复**扫描到。
如果写成"预约结束就 booking_count + 1"，扫描两次就加两次。

解法：用 `is_counted` 标记，加之前先检查：

```python
if not booking.is_counted:
    equipment.booking_count += 1
    booking.is_counted = 1
```

这样无论扫描多少次，结果都一样。

**验证结果**：

```
[第 1 次执行] 统计: {'scanned': 5, 'completed': 2, 'counted': 2}
             预约次数: 1 -> 3
[第 2 次执行] 统计: {'scanned': 3}
             预约次数: 3 -> 3     ← 没有重复累加 ✓
```

### 兜底反向扫描

正向扫描处理"预约 → 设备状态"。但还有一种脏数据：
**设备是 busy，却没有任何进行中的预约**
（比如服务在预约进行中被强制中断、或管理员手工改过状态）。

所以加了第二步反向扫描：找出所有 busy 但无活跃预约的设备，恢复为 available。
这种"正向处理 + 反向修正"的双向校验是数据一致性的常用手法。

## 六、邮件通知的修复（对比原项目）

**原项目的 bug**：

```python
# 原项目 routers/booking.py
asyncio.create_task(
    send_booking_created_email_async(booking_id, user_id, equipment_id, db)
)
```

后台任务**复用了请求级的数据库会话**。而 `get_db()` 在请求结束时会
`await session.close()`，后台任务是在响应返回**之后**才执行的 ——
此时会话已关闭，再去查数据就报错。表现是"邮件时好时坏"。

**V2 的解法**：

```python
async def notify_booking_created(self, booking: Booking) -> None:
    user_info = self._build_user_info(booking)       # 在请求内组装纯数据
    booking_info = self._build_booking_info(booking) # 不传 ORM 对象
    await self._send_in_thread(...)                  # 后台只拿纯字典发邮件
```

三个要点：
1. 在**请求内**（会话有效时）把数据组装成纯 Python 字典
2. 后台任务**完全不碰数据库**
3. 同步的 smtplib 调用用 `run_in_threadpool` 丢到线程池，不阻塞事件循环

**这个原则可以推广到所有"请求内启动、请求后执行"的任务**
（后台任务、消息队列消费者、定时任务）：
**不要跨边界传递数据库会话或 ORM 对象，只传纯数据。**
ORM 对象跨会话还会遇到 detached instance 问题（访问未加载属性直接报错）。

## 七、本批踩坑记录

| # | 现象 | 根因 | 解法 |
|---|------|------|------|
| 1 | 8 个并发请求产生 8 条重复预约 | **MySQL REPEATABLE READ 快照读**，锁串行化了但读到旧快照 | 冲突查询加 `with_for_update()` 改成当前读 |
| 2 | 预约总是失败提示"超过 10 条上限" | 测试数据累积污染（每次测试都插入新预约） | 测试前重置数据库；种子数据留足余量 |
| 3 | 维护中的设备未来时段也被拒绝 | 把"设备此刻的状态"当成了"预约那天的状态" | 去掉该检查，最终判断权交给管理员审核 |
| 4 | 重叠测试"通过"但原因是限流 | 限流把请求拦成 429，测的是限流不是冲突逻辑 | 加 `RATE_LIMIT_ENABLED` 开关，测试时关闭 |
| 5 | 种子数据只覆盖部分状态 | 前端 5 种状态的样式没法验证 | 种子数据覆盖全部 5 种状态 |

**坑 4 特别值得说**：这是一种"假通过"——测试显示绿色，
但验证的根本不是想验证的东西。**测试必须确认它失败的方式是对的**，
否则比没有测试更危险。

## 八、性能相关的设计说明

### 1. 锁的粒度选择

| 粒度 | 并发能力 | 说明 |
|------|---------|------|
| 锁整张表 | 极差 | 所有用户互相阻塞 |
| **锁单个用户**（本项目） | 好 | 同一用户串行，不同用户互不影响 |
| 锁单台设备 | 好 | 但无法防"同一用户约两台设备" |
| 同时锁用户+设备 | 中 | 可能死锁（各持一把等另一把） |

本项目选**用户维度**：能防住最核心的场景（同一用户狂点提交），
并发能力最好。设备维度的冲突由"当前读检测"兜底。

### 2. 预检接口不加锁

冲突预检（`/check-conflict`）用的是 `_readonly` 版本的查询，**不加行锁**。
理由：预检是只读操作，如果加锁，用户每点一次"检查可用性"
就会阻塞其他用户的正常预约，把并发能力拖垮。

预检结果本来允许"稍微不准"（提交时会用加锁版本严格校验）。
这是"按场景选择锁策略"的例子：**写操作必须严格，读操作可以放宽**。

### 3. 定时任务缩小扫描范围

`list_in_progress` 只查 `status='approved'` 的预约。
为什么不做日期过滤？
原项目为了性能只查今日/明日，但那样会**漏掉"过期很久但没被扫到"的预约**
（比如服务停了一周再启动）。

V2 的选择是查全部 approved（数量天然有限，因为只有未来的才可能是 approved），
在 Python 侧判断时间。文档里也写了：如果数据量大到需要优化，
正确做法是加日期**下限**过滤（`booking_date >= CURDATE() - INTERVAL 7 DAY`），
既能利用索引又不会漏数据。
